# Tom Autodev 套件评审与退出标准

标准 ID：`TAD-REVIEW-EXIT` · 版本：`1.0` · 生效日期：`2026-09-22`

**结束条件是：固定范围内的必要行为已有证据，重大缺陷已消除，剩余风险已有明确处置。无需等到所有模型都提不出建议。** 本文件定义验收规则，不代表当前版本已经通过验收。

## 1. 适用范围与唯一基准

本标准用于评审 `tom-autodev-suite` 自身的控制器、协议、schema、skill、适配边界和维护文档。通过 `tom-review` 评审 BGW/XFlow 等业务 Change Set 时，仍使用业务 Spec、项目规则和 [Review 阶段合同](../tom-review/references/phase-contract.md)，不替换其 JSON 字段、分类或 gate。

本文件是套件评审的唯一退出标准。仓库入口只引用它，不复制另一套门槛。`CHANGELOG.md`、旧评审报告和模型建议是证据线索；判断当前行为仍需核对本轮代码。

每轮开始固定以下内容，评审途中不自行扩大：

| 项目 | 必须记录的内容 |
|---|---|
| 目标 | 控制面工程验收 C、模型资格 M、真实平台资格 P，或其中的局部变更复核 |
| 代码基线 | 仓库、分支、完整 `target_commit`；差分评审另记完整 `base_commit` 与实际文件范围 |
| 规则基线 | 本标准版本和文件 SHA-256；适用的 workflow/profile/schema/skill 版本或内容 hash |
| 范围 | 本轮要验证的能力、支持的运行环境、相关入口/调用方；不适用项须说明依据 |
| 负责人 | 评审发起人或其指定维护者负责范围和剩余风险决定；模型不能代其批准 |
| 预算 | 本轮评审方式和修复复核次数；未指定时采用第 5 节默认值 |

正式退出结论只绑定已提交的 `target_commit`。工作区预审可记录 diff、未跟踪文件清单及内容指纹，但提交后还需核对最终内容。分支名、`HEAD` 或“最新版”不能替代完整 commit。标准、范围或代码改变时记录差异；旧结论只可作为明确继承的证据，不能原样挪给新版本。

## 2. 必须保持的行为与场景

下面是工程验收 C 的最低矩阵。表内测试文件是取证入口，**文件存在、用例数量多或历史全绿都不等于这些行为已经验证**。报告需逐项给出实际用例/静态证据、命令结果或缺口；必要时新增针对真实缺陷的回归。

| ID | 不变量 | 必验场景及现有取证入口 |
|---|---|---|
| WF-01 | 脚本决定状态迁移和内容校验；模型只在规定的 producer 边界产出内容，不凭声明取得完成资格 | 非法 schema、错 task/revision/前驱、Spec/DAG 验收点不一致均被拒绝；可修正的草案不永久锁死 job；Review 的澄清/未完成不能通过。见 [producer validation](../tom-autodev/scripts/tests/test_producer_validation.py)、[schema validation](../tom-autodev/scripts/tests/test_schema_validation.py) |
| WF-02 | 审批只授权准确的动作、输入和版本；重发、重放不扩大授权 | 错 hash、拒绝、过期、重复回应不能放行；合法重发可消费且重试有界；内容变更不能复用旧批准。见 [approval gate retry](../tom-autodev/scripts/tests/test_approval_gate_retry.py)、[approval channels](../tom-autodev/scripts/tests/test_approval_channels.py) |
| WF-03 | 任务、仓库、工作区和版本绑定可追溯；不覆盖用户改动 | 错仓/错分支/无基线阻断；脏工作区和中断后的自有改动按所有权处理；实现与独立产品测试保持同一任务合同。见 [workspace recovery](../tom-autodev/scripts/tests/test_workspace_recovery.py)、[task safety](../tom-autodev/scripts/tests/test_task5_safety.py) |
| WF-04 | 检查点与外部操作恢复不会丢失进度或盲目重复副作用 | 在记录、提交、回执和转移之间中断；重启消费已保存草案/审批；结果不明先核对，不能当成功或直接重发。见 [phase protocol](../tom-autodev/scripts/tests/test_phase_protocol.py)、[iCode runtime](../tom-autodev/scripts/tests/test_icode_runtime.py)、[state/artifacts](../tom-autodev/scripts/tests/test_state_and_artifacts.py) |
| WF-05 | 并发控制与幂等保证在实际调用路径成立 | 两个 worker 驱动同一 run、不同 run 竞争同一工作区、租约过期与重放；核对宿主锁的装配和无锁调用的边界，不能只看锁类单测。见 [orchestrator](../tom-autodev/scripts/tests/test_orchestrator.py)、[worker 接入](OPERATIONS.md#worker-接入) |
| WF-06 | 构建只证明冻结计划中准确版本、依赖和环境的结果 | 修复后旧 build 失效；共享测试变化使相关模块重新验证；独立未变模块按合同复用；多模块无遗漏、乱序恢复不串证据。见 [pipeline plan](../tom-autodev/scripts/tests/test_pipeline_plan.py)、[iPipe runtime](../tom-autodev/scripts/tests/test_ipipe_runtime.py) |
| WF-07 | 只有全部必需模块的匹配发布证据才能认定发布成功 | 缺模块、错 build/revision、旧环境、平台未发布均不能成功；G9 绑定本次完整证据；直接摄取/推进与 worker 入口遵守相同约束。见 [release evidence](../tom-autodev/scripts/tests/test_release_evidence_pinning.py)、[pipeline plan](../tom-autodev/scripts/tests/test_pipeline_plan.py) |
| WF-08 | 规则、配置和计划漂移不能继续使用不相容的旧授权 | workflow/profile 变化在可写入口的副作用前阻断；允许的只读回放不改状态；历史 run 恢复有明确前提，不能手改 hash 绕过。见 [execution guards](../tom-autodev/scripts/tests/test_execution_guards.py)、[workflow spec](../tom-autodev/scripts/tests/test_workflow_spec.py)、[profile repin](../tom-autodev/scripts/tests/test_profile_repin.py) |
| WF-09 | 诊断可表达真实失败，修复预算由持久化事实决定 | 有根因但尚无补丁的提案、源码 Review 失败身份、环境失败分类；重启不重置预算；同根因能累计、不同根因不混淆；达到上限停止或升级。见 [repair protocol](../tom-autodev/scripts/tests/test_phase_protocol_repair.py)、[repair policy](../tom-autodev/scripts/tests/test_repair_policy.py)、[failure signatures](../tom-autodev/scripts/tests/test_failure_signatures.py) |
| WF-10 | 完成结论、回执和复用证据真实且身份匹配 | 假/缺回执、旧产物、跨 prompt/model 缓存不能作证；日志/文档不泄露凭据；本地模拟结果不能冒充业务 iPipe 或真实发布结果。见 [runtime contracts](../tom-autodev/scripts/tests/test_runtime_contracts.py)、[run summary](../tom-autodev/scripts/tests/test_run_summary.py)、[行为场景](../evals/README.md) |

全量工程验收不能把这些核心项统一标为不适用。局部复核可以继承既有证据，但必须指明来源基线、影响分析和仍有效的理由。范围外发现可信的 P0/P1 风险仍要报告，不能用范围标签掩盖已知重大问题。

## 3. 什么算缺陷，什么只是建议

每条 finding 采用稳定 ID，至少包含：

1. **违反的约定**：`WF-xx` 或具体已承诺的合同、支持环境、验收点；引用原文位置。
2. **触发与影响**：输入/前置条件、入口、预期行为、实际行为、影响对象和严重级别。
3. **当前证据**：固定 commit 的代码路径/行号、调用链、失败用例或脱敏平台回执；静态证明也可成立，不要求为证明问题执行真实提交/发布。
4. **反证核对**：相关上游/下游守卫、已有恢复路径和测试为什么没有排除该触发条件。
5. **处置**：确认、驳回、待取证或改进建议；确认缺陷另记修复状态、复核证据，或风险接受记录。

“可能出错”“代码太长”“另一个模型觉得不好”“业界一般这样做”不能单独确认为缺陷。明显的授权、数据完整性等风险即使没有对应条款，也应记为合同缺口并取证，不能因矩阵没写而忽略。

| 级别 | 判定依据 | 退出要求 |
|---|---|---|
| P0 | 可导致严重越权、凭据泄露、不可逆数据损坏等紧急风险 | 修复并验证前不能通过验收 |
| P1 | 在支持场景下破坏核心承诺，例如误提交/误发布、旧证据放行、正常流程不可恢复地卡死、修复无限循环 | 修复并验证前不能通过验收 |
| P2 | 有证据的局部功能/恢复/兼容缺陷，影响有限，存在经验证的可行绕行方式 | 修复，或由负责人明确接受/延期并记录理由、绕行、负责人和到期/重开条件 |
| P3 | 不改变已承诺结果的可读性、重构、额外能力或优化建议 | 进入改进清单，不阻塞本轮退出 |

严重级别由触发条件和实际后果决定，不能为了收敛降级。P0/P1 不因评审预算耗尽或模型“接受风险”而放行。P2 没有明确接受决定就仍是待处理项；旧限制说明不自动构成风险接受。

同根因、同合同的不同表述合并为一项，保留多个触发例。新证据推翻驳回理由、扩大实际影响或证明修复无效才重开。待取证不是确认缺陷；但影响必要结论的事实未查明时，也不能写“通过”。

上述处置用于**套件维护报告**，不向业务 `review` DraftContent 增加分类或字段。

## 4. 三种验收结论分别给出

| 层级 | 通过条件 | 不能据此推断 |
|---|---|---|
| C：控制面工程验收 | WF 矩阵证据齐全；必要回归通过；无未解决的确认 P0/P1；P2 均已修复或获明确接受；影响结论的待取证项已关闭；完成第 5 节有界评审 | 某模型必然遵守 skill、真实内网平台可用 |
| M：模型/skill 资格 | 对确切模型版本、prompt/skill hash、控制器版本运行固定行为集；默认 [8 个场景](../evals/skill-scenarios.json) 每个独立上下文执行 3 次，必需决定及合同校验全部通过，无禁止动作、伪造证据；保存原始响应和判分依据 | 任意模型、未来任意需求均不退化；一轮单模型通过不能声明跨模型等价 |
| P：真实平台资格 | 在授权且具有代表性的真实项目/环境完成正常交付、失败→诊断→修复、审批后续跑/中断恢复；声称支持的多模块/人工阶段也须有真实证据；记录 run、CR/revision、build、环境、审批和发布核验，负责人确认结果 | 换项目/环境、扩展能力后仍自动有效 |

未测试的层级写“未验证”，不能填通过；当前工作只满足局部复核时写明局部范围。生产就绪需适用的 C、所选模型的 M 和目标环境的 P 同时成立。

更换模型时先固定相同输入和判分标准，分别跑 M，再与现用模型比较必要决定、合同成功率、人工干预次数；若另有成本/时延目标，应在运行前固定阈值。不能凭模型名称或一次漂亮输出替代资格验证。新增真实失败场景进入下一版固定场景集，使后续需求复用回归。

完整 C 验收的现有本地命令，从仓库根目录执行：

```bash
python3 -m unittest discover -s tom-autodev/scripts/tests -p 'test_*.py' -q
python3 -m unittest discover -s tom-review/tests -p 'test_*.py' -v
bash tom-diagnose/tests/test_autodebug.sh
git diff --check
```

这些只验证套件自身；业务编译/测试仍走 iPipe。局部变更按影响选择检查：普通文档做链接、命令/事实核对；技能指针做链接与 frontmatter 校验；模型决策规则变化做相关行为场景；控制器改动做受影响回归，完整 C 退出时运行上述完整检查。不要为不变内容反复全量测试，也不要把本次文档检查写成 C/M/P 通过。

## 5. 评审何时停止、何时重开

1. **首次 C 基线，或状态机/授权/持久化/发布绑定的实质变更**：对同一固定基线取得两份独立评审。可以是不同模型、不同人或独立上下文；先各自检查，再合并结果，不用上一份结论诱导第二份找同样问题。两份报告都受本标准和同一范围约束，不把两个模型意见相同当作证明。
2. **核验与修复**：合并重复项，只实施已确认的修复。缺陷回归证明失败触发被修复，同时核对相关调用方和正常路径。不能只修改提示词让评审不再报告它。
3. **定向复核**：后续只检查修复 diff、受影响不变量和回归。两份初审的有效证据可通过这些复核追溯到最终 commit；代码结构/范围实质变化时，相应初审结论失效，重新指定受影响范围。无需每修一项都再让所有模型重扫全仓。
4. **默认预算**：一个批次最多两轮“修复→复核”。仍有阻断就记录 `BLOCKED` 或 `INCOMPLETE`，给出未解决项、负责人和下一步，转为明确修复/架构任务；停止开放式评审。预算耗尽不等于验收通过，也不能自动另开同样的评审批次继续循环。
5. **退出**：必要条件全部满足时给出该层级的 `PASS`，记录最终 commit、继承/新增证据和残余风险；停止征集“还能优化什么”。已有通过基线后的普通文档/局部改动仅做对应复核，不自动重做首次全量流程。
6. **重开**：出现新的可验证 P0/P1、真实运行违约、修复回归失败，或代码/合同/环境/模型变化使原证据失效时，按影响重开相应层级。重构偏好、重复表述和额外功能愿望进入下个版本的改进清单。

标准增删或改变验收门槛须提升版本并说明原因。本轮按启动时固定版本评审；必要的紧急变更显式记录，不能在见到结果后悄悄放宽标准。发现新的重大风险必须报告，但“新增需求”不应伪装成旧版本未完成。

## 6. 让每次评审使用它

- **仓库发现**：根目录 `AGENTS.md` 指向本文件；`CLAUDE.md`、`GEMINI.md` 指向同一入口。支持这些约定的工具在仓库内开始任务时可加载规则。`tom-autodev` 和 `tom-review` 也为套件自身评审提供条件入口。
- **跨工具使用**：不自动加载仓库规则、或只接收粘贴代码的模型，必须同时提供本文件内容和下面的固定评审请求。仅粘贴路径给无法读取仓库的模型无效。
- **报告验收**：缺少标准身份、完整代码基线、范围或证据的报告记为 `INCOMPLETE`；可保留有用线索，但不能拿它作为验收通过或开启无界修改的依据。报告里的独立可验证重大缺陷仍应处理。
- **执行边界**：这些文件是指令发现和人工验收规则，当前未接入 CI/分支保护或报告校验器。它们不能保证任意工具必读、任意模型必从。后续如接入自动 gate，应机械检查身份/范围/证据完整性，语义真实性仍由测试和核验负责，不能只检查模型是否写了 `PASS`。

可复制的评审请求：

```text
请先读取 AGENTS.md 和 docs/WORKFLOW_EXIT_CRITERIA.md，并按其中固定格式评审。
本轮目标：<C / M / P / 局部复核>；范围：<能力、文件与支持环境>。
基线：base_commit=<完整 SHA；全量评审可不填 base>，target_commit=<完整 SHA>。
报告声明标准版本及 SHA-256，逐项列证据与未覆盖项。
只将有合同、触发条件、影响和当前证据的问题列为缺陷；改进建议单列。
复核时只看修复和影响面，沿用 finding ID；满足退出条件就停止。
无法读取规则/代码或缺关键证据时返回 INCOMPLETE，不猜测通过。
```

```markdown
- 未验证项与下一步：<值或无>；停止/重开原因：<值>
```

`BLOCKED` 表示已确认的退出阻断；`INCOMPLETE` 表示缺少必要范围、证据或决定。两者并存时主结论用 `BLOCKED`，并列出缺证据项；没有完整证据不能由“没发现问题”推导 `PASS`。

首次建立基线时，从 [整合报告](../SKILL_CONSOLIDATION.md)、[行为评测记录](../evals/README.md) 和 [更新记录](../CHANGELOG.md) 提取待核验线索，再核对目标 commit。例如修复预算未接线的历史描述已在后续代码中更新，不能直接复制为新缺陷。本标准的加入不替现存限制作风险接受，也不补造跨模型或真实平台验收记录。
