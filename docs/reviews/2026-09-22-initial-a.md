## Findings

以下定位均指初审快照内的原始文件行号，不是修复后的工作区行号。

### A-01 / P1：generic advance 可在没有发布时进入 RELEASE_SUCCESS

- 合同：WF-07、WF-01、WF-10。
- 触发：run 到达真实 RELEASE frontier，具备匹配当前 action hash 的 G9，传入 `artifacts=["release-evidence"]`、相等 revisions 和正确的 pinned environment fingerprint。
- 预期：必须确认全部必需模块的真实平台发布证据。
- 实际：`scripts/orchestrator.py:1115` 经过通用 EvidenceGate 后提交成功；`scripts/evidence_policy.py:91` 只检查 artifact 名称成员关系；维护 CLI `_advance` (`orchestrator.py:3460`) 可达。
- 影响：零平台发布、零 RELEASE artifact 的 run 被写为 RELEASE_SUCCESS。
- 反证核对：worker 与 ingest 的 all-module/platform verification 是有效保护；但 `test_direct_release_cannot_bypass_other_modules_or_platform_verifier` 只覆盖 ingest，不覆盖 generic advance。

复现复用 `test_pipeline_plan.PipelinePlanTests`：`_start_plan()`、`_build("A", "a-ok")`、`_build("B", "b-ok")`，读取 `protocol.next(run)`，用 ledger 创建准确 G9，然后执行：

```python
orch.advance(run, "RELEASE_SUCCESS", {
    "input_hash": action["input_hash"],
    "approval_id": approval["approval_id"],
    "artifacts": ["release-evidence"],
    "repo_revisions": action["source_revisions"],
    "evidence_revisions": action["source_revisions"],
    "evidence_environment_fingerprint": canonical_hash(profile["environment_profile"]),
})
```

实际结果 OK/RELEASE_SUCCESS；`api.releases == []`；RELEASE artifacts 为 `[]`。

### A-02 / P1：合法重发 gate 不能被 producer/worker 消费

- 合同：WF-02、WF-04。
- 触发：原始审批终结后，合法重发生成 `G4#retry-1`，在真实独立 ledger 中批准同一 PLAN draft hash。
- 预期：base gate 与 retry gate 按相同已批准行为消费。
- 实际：`worker_driver.py:73,157` 和 `evidence_policy.py:57` 将 action 与裸 gate 字面相等比较。`PhaseProtocol._approval_error` 在 `phase_protocol.py:1135` 已用 `gate_of` 规范化，但随后 EvidenceGate 再次拒绝。
- 复现：`test_producer_validation.ProducerValidationTests` 的 `frontier("PLAN")` → `submit()` → `approve("G4#retry-1", hash)` → 再 `submit()` 仍为 APPROVAL_REQUIRED；直接 `complete_phase(build_envelope(action, draft, retry_approval_id))` 也被拒绝。
- 影响：TIMEOUT 记录不可改，合法草案无法凭空改 hash；没有验证到合法恢复绕行。
- 反证核对：iCode/iPipe `_approved_record` 已正确处理 retry；现有 retry 测试只覆盖这两处。collaboration G0 和 watcher handoff 存在同根字面比较，合并在本 finding 内。

### A-03 / P1：没有现成 diff 的修复建议无法进入 PLAN

- 合同：WF-09 明确要求“没有现成 diff 的修复建议”场景。
- 触发：DIAGNOSE 证据足够、`route=REPAIR`、`scope=CODE_ONLY`，尚未生成修复代码，因此 `repair_diff_hash=None`。
- 实际：`schema_validator.py:462–465` 要求 REPAIR 的 diff hash 非空；JSON diagnosis schema 允许 null。
- 影响：`tom-diagnose/SKILL.md:24` 禁止 DIAGNOSE 产出补丁；先有 diff 才能完成诊断，且到 PLAN 的路由只在诊断完成后发生 (`phase_protocol.py:1251`)，形成闭环。
- 复现：现有 diagnosis fixture 除 `repair_diff_hash=None` 外保持合法，protocol validator 返回 SCHEMA_INVALID / `repair_diff_hash:missing`。
- 反证核对：`test_schema_validation.py:92–99` fixture 始终预填虚构的已有 hash，因此绿测没有覆盖真实无 diff 起点。

### A-04 / P1：来源为 Review 的诊断没有可表达的真实身份

- 合同：WF-09。
- 触发：源码 Review 拒绝后进入 DIAGNOSE (`phase_protocol.py:1209`)，还没有流水线 build/stage/job。
- 实际：`schemas/diagnosis.schema.json:1` 对全部 route 强制非空 `build_id/stage_id/job_id`。
- 影响：action 只有 Review artifact/task/revisions 身份；没有非 pipeline identity mapping。`tom-diagnose/references/phase-contract.md:7` 禁止伪造流水线 IDs，诚实 producer 无法完成。
- 复现：复用 `PhaseProtocolPredecessorBindingTests.action_for(...DIAGNOSE, REVIEW,...)`；采用 `route=SPEC`、`repair_diff_hash=None` 排除 A-03 干扰，IDs 为 None，结果 SCHEMA_INVALID，三项 identity invalid；缺失/空字符串也不能通过。
- 反证核对：现有 Review 路由测试证明会进入 DIAGNOSE，但没有完成其后的真实非流水线诊断。

### A-05 / P1：缓存 iPipe runtime 在 profile 漂移后仍写平台

- 合同：WF-08，profile 变化须在可写入口副作用前阻断。
- 触发：通过真实 `Orchestrator.ipipe_runtime` 工厂构造 runtime，取得并批准准确 G7；随后磁盘 profile 的 image_digest 改变；复用旧 runtime 和旧 profile 参数触发。
- 实际：工厂仅在构造时校验。`clients/ipipe_runtime.py:840–852` 只比较调用参数与缓存 `validated_profile`；`execution_guard.py:27` 只检查 workflow；`trigger` 在 `clients/ipipe_runtime.py:188` 发出写操作。
- 复现：`PipelinePlanTests._start_plan()` 后使用真实工厂；临时 profile 的 `environment_profile.image_digest="sha256:changed"`；`orch._runtime_profile` 明确返回 PROFILE_CONFLICT，但旧 runtime 调用 mock `trigger_by_revision("pipe-A", "a1", {})` 一次。随后返回 TRIGGER_CONFIRMATION_REQUIRED，已晚于外部写。
- 影响：审批基于旧环境/配置，平台动作却能在 run 已冲突时发出；后续 ingestion 拒绝不能撤销已触发构建。
- 反证核对：原有 profile test 只修改传入 profile 与缓存副本的差异，没有覆盖构造后的磁盘变化。
