# NPL simulator evidence

NPLSIM exercises a behavioral model generated by the front-end. Compilation, model behavior, back-end placement, and device behavior provide different evidence; a passing model test does not prove that the target chip accepts the program.

The historical Debug User Guide §2.6 excludes dynamic tables (VFP/IFP/EFP/EM FT), hardware learning, and flex counters from its NPLSIM profile. Use that list to ask for the current pinned simulator's capability matrix, not to assert that all releases share the same limits. If a required assertion is unsupported, require the project profile's hardware or other supported verification stage; do not silently skip the assertion.

For a behavior mismatch retain input packet bytes and port identity, table setup/read-back, expected output/drop behavior, actual output bytes, and relevant model logs. Follow parser extraction → lookup key/hit/action → function/bus values → editor operations → final output; internal traces locate the cause while external packet/API behavior remains the acceptance boundary. Keep input/expected results independent of generated implementation details.

This reference describes which remote evidence to request and read. Compiler/model commands and environment configuration stay in the pinned iPipe runner. See [sources](sources.md) for the guide provenance.
