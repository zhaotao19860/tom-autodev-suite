## Critical Findings

### C1. Artifact identifiers can escape the artifact root and make the store read or write outside its ownership boundary

`ArtifactStore` keeps the caller-supplied root unresolved ([scripts/artifact_store.py:15](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:15)) and concatenates unvalidated `run_id` and `kind` path components directly into the artifact directory ([scripts/artifact_store.py:55](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:55)). An absolute component discards the configured root, while `..` components traverse above it. `put()` then creates that directory and writes `content.bin` and `metadata.json` there ([scripts/artifact_store.py:58](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:58), [scripts/artifact_store.py:133](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:133)). `get()` likewise trusts the paths stored in SQLite without checking that their resolved targets remain under `self.root` ([scripts/artifact_store.py:99](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:99)). Symlinked path components are not rejected either.

This violates artifact confinement and lets malformed identifiers create or consume evidence outside the store. It also makes a relative root non-durable across processes launched from different working directories because relative paths are persisted verbatim. Resolve the root once, validate or encode each logical component, reject symlinks/escapes, and verify every persisted path with `relative_to(root)` before reading. The artifact tests use only safe fixed identifiers and absolute temporary roots ([scripts/tests/test_state_and_artifacts.py:25](/Users/tom/Desktop/skills/tom-autodev/scripts/tests/test_state_and_artifacts.py:25)); they do not cover absolute components, `..`, symlinks, or a changed working directory.

### C2. Durable state helpers persist secret-bearing payloads and metadata verbatim

The hard boundary forbids persisted secrets, but all generic durable payload paths serialize caller dictionaries without secret-key rejection or redaction: events ([scripts/state_store.py:109](/Users/tom/Desktop/skills/tom-autodev/scripts/state_store.py:109)), external intents ([scripts/state_store.py:184](/Users/tom/Desktop/skills/tom-autodev/scripts/state_store.py:184)), receipts/external results ([scripts/state_store.py:221](/Users/tom/Desktop/skills/tom-autodev/scripts/state_store.py:221)), and handoffs ([scripts/state_store.py:290](/Users/tom/Desktop/skills/tom-autodev/scripts/state_store.py:290)). Artifact metadata is also encoded and written as plaintext ([scripts/artifact_store.py:47](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:47), [scripts/artifact_store.py:62](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:62)). A response or handoff containing `token`, `authorization`, `password`, or credentials will therefore be copied into SQLite or JSON permanently.

Task 2 already has recursive secret-key detection/redaction, but these Task 3 persistence boundaries do not use an equivalent policy. Because external responses are precisely where tokens and credential-bearing diagnostic data can appear, relying on every future adapter to remember filtering is not fail-closed. Reject secret-bearing payload paths before persistence (or accept only typed allowlisted envelopes), and add tests that inspect both SQLite and artifact files without ever echoing the supplied secret values.

## Important Findings

### I1. Re-putting a corrupted artifact silently reports success while leaving it corrupted

`_write_once()` returns immediately for any existing path without verifying its bytes ([scripts/artifact_store.py:130](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:130)). `put()` then uses `INSERT OR IGNORE`, never compares an existing index row with the expected run/kind/paths/hashes, and unconditionally returns the requested artifact descriptor ([scripts/artifact_store.py:63](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:63), [scripts/artifact_store.py:82](/Users/tom/Desktop/skills/tom-autodev/scripts/artifact_store.py:82)). After content or metadata is corrupted, an idempotent retry of the same `put()` therefore appears successful but does not repair or reject the invalid object; only a later `get()` exposes the mismatch.

Fail closed when either an existing file or index row differs, or atomically replace/quarantine and revalidate before returning. The tests prove that `get()` rejects a post-write mutation ([scripts/tests/test_state_and_artifacts.py:105](/Users/tom/Desktop/skills/tom-autodev/scripts/tests/test_state_and_artifacts.py:105)), but do not retry `put()` after corruption or exercise a conflicting pre-existing index row.

### I2. Worktree creation has a baseline TOCTOU window and no containment-safe cleanup lifecycle

`create()` verifies source `HEAD`, then performs additional status/branch reads and filesystem creation before `git worktree add` ([scripts/workspace_manager.py:85](/Users/tom/Desktop/skills/tom-autodev/scripts/workspace_manager.py:85), [scripts/workspace_manager.py:95](/Users/tom/Desktop/skills/tom-autodev/scripts/workspace_manager.py:95), [scripts/workspace_manager.py:98](/Users/tom/Desktop/skills/tom-autodev/scripts/workspace_manager.py:98)). A concurrent checkout or commit in that interval is not rejected; the method returns `CREATED` from the recorded revision even though the source baseline changed, contrary to the explicit changed-baseline rejection requirement. The created worktree itself is detached at the requested commit, but the prerequisite that the recorded source baseline is still current is not atomic.

The configurable `worktree_root` is also never checked to be outside the source checkout ([scripts/workspace_manager.py:10](/Users/tom/Desktop/skills/tom-autodev/scripts/workspace_manager.py:10), [scripts/workspace_manager.py:90](/Users/tom/Desktop/skills/tom-autodev/scripts/workspace_manager.py:90)). Parent directories are created before Git runs, and a failed add returns without removing those directories or pruning a partial Git worktree registration ([scripts/workspace_manager.py:97](/Users/tom/Desktop/skills/tom-autodev/scripts/workspace_manager.py:97), [scripts/workspace_manager.py:99](/Users/tom/Desktop/skills/tom-autodev/scripts/workspace_manager.py:99)). There is no successful-worktree cleanup interface. Recheck `HEAD` after creation, clean up and fail on change, reject any root at/under the source worktree, and provide idempotent `git worktree remove`/`prune` cleanup. Current tests cover only sequential success and pre-call revision change ([scripts/tests/test_workspace_recovery.py:20](/Users/tom/Desktop/skills/tom-autodev/scripts/tests/test_workspace_recovery.py:20), [scripts/tests/test_workspace_recovery.py:50](/Users/tom/Desktop/skills/tom-autodev/scripts/tests/test_workspace_recovery.py:50)).

### I3. Concurrent duplicate approval requests are not atomic or idempotent

`ApprovalLedger.request()` performs a read-before-insert in a deferred transaction, without `BEGIN IMMEDIATE` ([scripts/approval_ledger.py:58](/Users/tom/Desktop/skills/tom-autodev/scripts/approval_ledger.py:58)). Two Comate/Infoflow publishers requesting the same `(action, input_hash)` can both observe no row and then race on the unique index; one request will fail with a SQLite lock or uniqueness error instead of returning the already-created shared `approval_id`. This undermines the required single shared approval identity under the exact multi-channel delivery scenario the ledger supports.

Serialize request creation as the intent/receipt methods do, then re-read the winning row on uniqueness conflict. The existing idempotency test invokes requests sequentially only ([scripts/tests/test_gates.py:281](/Users/tom/Desktop/skills/tom-autodev/scripts/tests/test_gates.py:281)); it does not start competing requests.

### I4. The production `resume` command bypasses Task 3 recovery and can report readiness without querying uncertain intents

`Recovery.resume()` correctly converts every pending intent into an ordered `QUERY_EXTERNAL_STATUS` action and sets `retry_allowed` false ([scripts/recovery.py:21](/Users/tom/Desktop/skills/tom-autodev/scripts/recovery.py:21)). However, the actual orchestrator resume entry point still delegates to plain status ([scripts/orchestrator.py:65](/Users/tom/Desktop/skills/tom-autodev/scripts/orchestrator.py:65)), and the CLI routes `resume` to that method ([scripts/orchestrator.py:289](/Users/tom/Desktop/skills/tom-autodev/scripts/orchestrator.py:289)). A run with an intent committed immediately before a crash will therefore return its latest state through the supported command without any `QUERY_REQUIRED` action, lock/handoff report, or retry prohibition.

Wire the orchestrator to the recovery service (and make subsequent transition/side-effect paths honor `retry_allowed`) before describing query-not-retry recovery as executable control-plane behavior. The Task 3 tests call `Recovery` directly ([scripts/tests/test_workspace_recovery.py:142](/Users/tom/Desktop/skills/tom-autodev/scripts/tests/test_workspace_recovery.py:142)); the orchestrator resume regression still only checks state reporting and cannot catch this integration gap.
